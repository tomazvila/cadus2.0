# M6 — Offline authoring pipeline, review tooling, React + TypeScript SPA

Requirement IDs: A2, C6, T2, T3, T5, T6, C5, C1, L4, L5, O3.
Spec: `docs/reference/authoring-and-spa-1.0-spec.md` (the 1.0 authoring loop and yields,
the review surface, the 1.0 React + TS SPA in `web/` with its traps, design tokens, KaTeX
rules, pinned literals, and a 22-unit breakdown in §7).

## Fixed decisions (orchestrator)

- Start the SPA from 1.0's `web/` (React 19 + TS strict, Vitest + jsdom + Testing Library +
  MSW + vitest-axe, ESLint react-hooks + jsx-a11y, the invariant gate). Copy it into
  `web/` of this repo (C5: reviewed in git), keep the idioms and the 11 documented traps'
  fixes, and rewrite the API layer against `docs/reference/web-service-1.0-spec.md` §2.
  Nothing of `static/` is kept (O3).
- Toolchain on this box: node v22.21.1, npm 10.9.4. The browser click-through runs in the
  `mcr.microsoft.com/playwright:v1.62.1-noble` container (native Playwright needs root
  for its libraries); it is a separate CI step from the unit gate.
- Authoring runs in `cadus-worker` as a batch job (A2, R4), never in a request handler:
  per KP and kind (`template`, `teach`, `hint_ladder`, `diagnosis`): author → gate → retry
  with the literal rejection message as feedback; **5 attempts**, the T3 alert above 3;
  store as `pending` in `content_store` with `authoring_attempts` and `authoring_cost_usd`
  (T3); every call through the M5 model client with the T5 defaults and a T6 row with
  `purpose = 'authoring'`. Teach pages and hint ladders get authoring paths (new in 2.0:
  1.0 had none) with their own gates (a hint never contains the answer).
- Review (C6): admin-only HTTP routes (`/api/admin/content*`: list pending by KP, show
  rendered instances + gate notes, approve, reject) writing through an explicit admin
  path (`cadus_app` holds SELECT only on `content_store`), and the SPA review screen.
  Approval binds to the digest; an edited body is a new row.
- The SPA is served by Caddy from `dist/` on the same origin as `/api`; the runtime image
  carries no node (a node build stage in the Dockerfile).
- The design tokens of §4.2 (Tokyo Night) are carried over verbatim as a token
  stylesheet with a contract test.

## Units

Spec §7: R1–R8 (Rust: prompts, the batch loop, T3 accounting, `cadus_store::content`,
admin routes, teach/hint authoring, distractor authoring, the CLI + runbook) and S1–S14
(TypeScript: scaffold, API layer, hooks, design system, math input, auth screens,
dashboard, the session loop, the diagnosis panel, quiz + placement, the curriculum map,
operator + review screens, the click-through, packaging). Each ≤ ~400 lines with the
acceptance check named there.

Sequence: (R1 → R2 → R3) ∥ (R4 → R5) → (R6 ∥ R7) → R8; S1 → S2 → (S3 ∥ S4) → S5 →
(S6 ∥ S7) → S8 → (S9 ∥ S10 ∥ S11) → S12 → S13 → S14. The Rust chain and the TypeScript
chain run in parallel; S12 waits for R5. Then mutation check, review (2 rounds, major+),
fixes, close. M6 starts after the M5 close and the owner's go.
